OpenClaw Kalshi Bot - Full Documentation
========================================

1) What This System Is
----------------------

This is a Node.js + TypeScript automated Kalshi trading system with:

- Live/Dry-run execution engine
- Kalshi market adapter + orderbook normalization
- Pluggable strategy engine
- Market intelligence layer (quality, probability, execution modeling, edge gate)
- Auto-learning layer (decision journaling, attribution, shadow challengers, guarded promotion/rollback)
- Dashboard + APIs for control and observability
- OpenClaw Telegram notifications
- SQLite persistence for all runtime state

Primary runtime defaults are safety-oriented:
- DRY_RUN true by default
- LIVE requires explicit arm/confirm gates
- hard risk caps and kill switches

5) Runtime Strategy Flow
------------------------

Per scan tick:

1. Load runtime config
2. Apply active learning profile overrides (time window + gates)
3. Fetch candidate markets
4. Filter/rank scan pool
5. Pull orderbook + parse rules
6. Run strategy decision (BUY/NOOP)
7. Run intelligence evaluation:
   - quality score
   - model probability
   - fill probability + expected cost
   - edge gate
8. Enforce risk/exposure/correlation guards
9. Log decision for active profile + shadow profiles
10. Attempt top candidates only
11. On fill: create position, map decision->execution
12. On resolve: compute fee-aware pnl + attribution


6) Auto-Learning Design
-----------------------

Profiles:
- champion (active profile)
- cautious (more selective)
- opportunistic (less selective)

How learning works:

- Every decision is logged for all profiles (champion + challengers).
- Resolved positions are attributed with root cause labels, e.g.:
  - negative_or_zero_edge
  - low_fill_probability
  - low_market_quality
  - clock_drift_timing_risk
- Periodically, profile performance is scored:
  score = pnlUsd - 0.5 * maxDrawdownUsd + 2 * winRate
- Promotion requires:
  - minimum resolved sample size
  - challenger score lift over current profile
- Rollback trigger:
  - active profile with meaningful sample and sustained drawdown
  - auto-switch to cautious profile

Guardrail principle:
- learning adjusts selectivity, never bypasses hard risk controls.


7) Risk and Safety Controls
---------------------------

Execution hard guards include:
- maxOrderNotionalUsd
- maxOrdersPerDay
- duplicateCooldownSec
- maxOpenPositions
- dailyLossLimitUsd
- max total / per-symbol / per-location exposure
- correlation guard

Live gate:
- dryRun must be false
- live confirmation code required
- explicit acknowledge required
- live arm timeout auto-disarms

Kill switch:
- STOP_NEW_TRADES via commands file, dashboard API, and UI control.

11) Environment and Secrets
---------------------------

Non-secret runtime config:
- Stored in SQLite settings table

Secrets:
- Stored via secure store (keychain when available, encrypted fallback)
- LOCAL_MASTER_KEY required for encrypted fallback

Never log:
- private keys
- secret payloads
- Telegram bot tokens/secret config values


12) Troubleshooting
-------------------

A) No trades happen
- Check /api/stats for blocked reason
- Check market focus and gate strictness
- Check no stale open positions
- Check opportunities API and scan-test output

B) Too many requests / 429
- Reduce scan load (already includes cache/backoff)
- Lower topCandidatesPerTick
- Increase scan interval if needed

C) Clock drift warning
- Sync system clock in macOS Date & Time settings
- Drift-sensitive strategies degrade with high drift

D) Reconciliation auth denied
- Balance endpoint may pass while orders endpoint fails
- Ensure Kalshi key has required portfolio/order scopes

E) Live gate fails
- Ensure dryRun=false first
- Use current live confirm code from /api/settings
- Re-arm when arm timeout expires


13) Operational Recommendations
-------------------------------

Start small:
- maxUsdPerTrade = 1 to 2
- maxOpenPositions = 1
- dailyLossLimitUsd = 3 to 5

Scale only after:
- positive realized pnl
- acceptable drawdown
- stable fills
- stable API/reconciliation health

Use learning status:
- monitor activeProfile
- monitor top attribution causes
- inspect promotion events before raising risk
